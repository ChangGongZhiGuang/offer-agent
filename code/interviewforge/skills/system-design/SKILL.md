## 岗位画像
- **典型职级**：中高级（5+ 年）才会被认真问；初级通常只问一道软性
- **核心能力**：在 45 分钟内把模糊需求 → 量化指标 → 架构骨架 → 关键组件深挖 → 取舍说明
- **考察价值**：考的不是「你知不知道答案」，而是「你怎么在不确定下做工程决策」
- **本质**：这是一道开放题，候选人主导节奏，面试官只点拨

## 标准答题框架（4S + 2T）
1. **Scenario**（场景）：澄清功能需求、非功能需求
2. **Scale**（规模）：日活、QPS、存储量、带宽 —— **必须出数字**
3. **Storage**（存储）：表结构 / NoSQL / 缓存层 / 文件
4. **Service**（服务）：拆模块 / 同步 vs 异步 / 边界
5. **Trade-off**（权衡）：CAP、一致性强弱、成本 vs 性能
6. **Trace**（演进）：从最小可用版本开始，逐步加并发、加可靠性

候选人没遵循框架的话，面试官可以引导而不是直接打分低。

## 考察维度

### 1. 需求澄清与规模估算（权重 20%）
- 主动确认核心功能（最小集）vs 锦上添花
- 用费米估算给出数字：DAU × 人均行为 × 每条数据大小 = 日数据量
- 估带宽：QPS × payload；估存储：日量 × 保留天数 × 副本数
- 把 QPS 拆成读 QPS 与写 QPS，比例至少 10:1 还是 1:1

### 2. 架构骨架（权重 20%）
- 七层骨架：Client → CDN → LB → API GW → Service → Cache → DB/MQ/Search
- 拆服务边界：按业务域而非按表
- 同步 vs 异步：写请求落 MQ 还是直接落库

### 3. 数据存储选型（权重 20%）
- 关系库（MySQL/PG）：强一致、事务、ACID 场景
- KV（Redis）：缓存、计数、限流
- 文档（MongoDB/ES）：弹性 schema、搜索
- 列存（HBase/Cassandra）：海量写、宽行
- 时序（InfluxDB/Prometheus）：监控指标
- 图（Neo4j/Nebula）：关系查询
- 对象存储（S3/OSS）：图片/视频
- **必须能说 trade-off**：写放大、读放大、空间放大

### 4. 一致性、可用性与容错（权重 20%）
- 副本/分片/选主：Raft / Paxos / Gossip 模型
- 缓存一致性：旁路 / 双写 / 订阅 binlog
- 异地多活：单元化、读写分离的极致
- 灾备：RPO / RTO 数字
- 容错：限流（令牌桶）、降级（开关）、熔断（半开态）、隔离（线程池/舱壁）

### 5. 演进与权衡表达（权重 20%）
- 从单机版讲起，按 QPS 增长引入新组件
- 每个组件都能说「为什么不是 X」
- 能识别瓶颈：单点、跨地、慢查询、热点 key
- 能给数字而非「大概很慢」

## 经典题目与切入要点

| 题目 | 关键深挖点 |
|---|---|
| **短链系统（TinyURL）** | 短码生成策略（hash vs ID 编码）、防碰撞、跳转 QPS 极高怎么抗 |
| **秒杀系统** | 流量削峰、库存扣减一致性、防超卖、防黄牛、缓存预热 |
| **Feed 流（朋友圈/微博）** | 推 vs 拉 vs 推拉结合、大 V 粉丝爆炸、冷热数据 |
| **即时通讯（IM）** | 长连接（WebSocket）、消息可靠投递（ACK）、消息排序（递增 seq）、群消息扩散 |
| **分布式计数器（点赞）** | 写热点、Redis 异步刷库、批量合并 |
| **附近的人/外卖** | GeoHash、四叉树、Redis GEO |
| **新闻 Feed 推荐** | 召回 + 排序两阶段、向量召回、A/B 实验 |
| **限流器** | 令牌桶在分布式如何实现（Redis Lua 原子操作） |
| **分布式 ID** | Snowflake / 号段模式 / Leaf 的 trade-off |

## 追问树

### 答得好 → 持续加压
- 「数据量再 ×100 你这个方案哪里先撑不住？」
- 「现在要做异地多活，主要难点在哪？」
- 「读多写少你方案 A；如果突然反过来写多读少呢？」
- 「假设 MySQL 挂了 5 分钟你怎么降级？」

### 答得卡 → 给数字降维
- 「先别想分布式，单机 + 单 Redis 你能撑多少 QPS？」
- 「这个功能的核心数据模型有几张表？」
- 「最坏情况一条请求经过几次网络往返？」

### 答得发散 → 拉回主线
- 「这些点都重要，但你觉得最关键的瓶颈是哪个？」
- 「我们先把核心链路画完再谈优化」

### 答得太教科书 → 逼实战
- 「这个方案在你之前公司真做过吗？踩过什么坑？」
- 「你能画一下当时的真实架构吗？」

## 红旗信号

| 信号 | 含义 |
|---|---|
| **不估算就开始画** | 没规模感，画的方案没意义 |
| **一上来用 K8s/Service Mesh** | 拿大词吓人，没解决实际问题 |
| **不区分读写比例** | 缓存策略全凭背诵 |
| **CAP 背得溜但举不出 CP 系统例子** | 概念脱节 |
| **每个组件都用最复杂的** | 不会做取舍；好的设计是「足够简单」 |
| **不肯说『我不知道』** | 硬编 → 不可信 |

## 评分 rubric（每维度 1-5 分）

| 分 | 描述 |
|---|---|
| 1 | 没框架，乱画一通 |
| 2 | 有框架但漏关键模块 |
| 3 | 框架完整、组件选型合理、能给规模数字 |
| 4 | 能识别瓶颈，能讲多个方案的 trade-off |
| 5 | 能给行业真实案例做对比，能讲为什么主流公司选 A 而你选 B |

**通过线**：高级岗 3.5+；架构岗至少一维 5；能讲清「为什么不那么做」往往比能讲清「怎么做」更值钱。

## 与简历交叉验证清单
- 简历写「主导设计 X 系统」→ 让画当时架构图 + 讲容量规划
- 简历写「QPS X 万」→ 追问怎么压测、瓶颈在哪、当时机器配置
- 简历写「降本 X%」→ 追问优化项、ROI、副作用
- 简历写「主导异地多活」→ 必问单元化策略、数据一致性方案
